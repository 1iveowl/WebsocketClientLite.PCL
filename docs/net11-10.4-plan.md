# 10.4 plan: .NET 11 and C# 15

Written 2026-11-14. Release 10.4.0 adds the `net11.0` target and uses what C# 15 and
.NET 11 offer inside the library. It adds no feature and no public API. The work is three
topic branches into `releases/10.4.0.0`, created from `main` at `9a6fbcc`, one pull request
each, merged in this order. Releasing stays the owner's step.

| Step | Work | Branch | Needs |
| --- | --- | --- | --- |
| P1 | `net11.0` target, LangVersion 15, .NET 11 test host, tooling, CI, dev container, docs | `chore/net11-platform` | none |
| P2 | C# 15 inside the library: a union for the handshake outcome, collection expression arguments. **Deferred past 10.4.0** (decision 4): draft pull request | `chore/csharp-15` | P1, a Stryker release that compiles C# 15 |

## Owner decisions (2026-11-14)

1. Keep `net8.0` and `net9.0` although both reached end of support on 2026-11-10, the day
   .NET 11 shipped. Dropping them would move .NET 8 and 9 consumers to the
   `netstandard2.1` build, whose `#if` paths differ: a behaviour change in a release
   that promises none.
2. Turn on Runtime Async (`<Features>runtime-async=on</Features>`) for `net11.0` only, as
   its own pull request, with the full evidence run and before and after numbers. If the
   tests or the numbers argue against it, report that instead of adopting it.
3. Adopt C# 15 where it fits: LangVersion 15 for every target, a union for the internal
   handshake outcome, with internal polyfills of the three compiler types for the targets
   before .NET 11, and `with(...)` collection expression arguments. Labeled `break` and
   `continue` have nothing to replace here (no nested loops), so they are not used.
4. Later the same day, after Stryker failed on P2 (lessons 4 and 5): 10.4.0 ships
   `LangVersion` 15, the `net11.0` target and, if the evidence supports it, Runtime Async,
   but no C# 15 syntax. P2 stays on its branch as a draft pull request until a Stryker
   release compiles C# 15. The release notes say so.

## Facts checked on 2026-11-14

- .NET 11.0.0 and SDK 11.0.100 were released on 2026-11-10 (release metadata
  `releases-index.json`). C# 15 is the default for `net11.0`.
- With the 11.0.100 SDK and `LangVersion` 15, collection expression arguments and labeled
  `break`/`continue` compile for `netstandard2.0`, `net10.0` and `net11.0`. Union types need
  `System.Runtime.CompilerServices.IUnion` and `UnionAttribute`, and `closed` needs
  `IsClosedTypeAttribute`; only .NET 11 has them (errors CS0518 and CS0656 on the others).
- Runtime Async is off by default for `net11.0`: the SDK sets neither `Features` nor
  `UseRuntimeAsync`.
- Dafny 4.11.0 is self-contained on its own .NET 8 runtime, so the protocol job does not
  depend on the SDK version installed beside it.

## Lessons

1. **`Microsoft.Bcl.AsyncInterfaces` 11.0.0 does not support `net8.0` or `net9.0`.** Its
   build targets warn for both. The interface package references it unconditionally from
   its single `netstandard2.0` target, so the warning would reach every .NET 8 and 9
   consumer's build. Both projects stay on 10.0.14, with a comment in
   `IWebsocketClientLite.csproj`. Bump it with the decision to drop `net8.0` and `net9.0`,
   not before.
2. **The .NET 11 dev container images are Ubuntu 26.04 only.** `mcr.microsoft.com/devcontainers/dotnet`
   has `2-11.0` and `2-11.0-resolute` and no `noble` tag. CI host qualification requires
   Ubuntu 24.04, so the dev container keeps the `2-10.0-noble` image and its `dotnet`
   feature adds the 11.0 SDK. A move to 26.04 is its own change.
3. **The controlled experiments follow the newest target.** They, the Stryker runtime probe
   and Stryker itself used to name `net10.0`. They now use `Evidence.PrimaryTfm`
   (`net11.0`). That matters for P3: Runtime Async changes the `net11.0` build only, so the
   race experiments must run against that build to say anything about it.
4. **Stryker.NET cannot compile C# 15 yet, and it does not say so.** Stryker compiles
   mutants with the Roslyn it bundles, not the SDK's. Stryker 5.0.0 and 5.1.0 (the newest,
   released 2026-11-10) both bundle Roslyn 5.9.0-1, whose newest language version is C# 14;
   SDK 11.0.100 has Roslyn 5.12.0. Since 5.1.0 Stryker reads the project's `LangVersion`,
   and a value its Roslyn does not know, such as `15.0`, falls back to Default (C# 14)
   without a warning. The maintainers confirmed this in stryker-net PR #4001; PR #4012
   updates Roslyn to 5.12.0. The P1 Stryker run is still valid, because the P1 source has
   no C# 15 syntax. P2 puts a `union` and `[with(...)]` into `WebsocketConnectionHandler.cs`,
   the file Stryker mutates, so Stryker is expected to fail to compile it until a Stryker
   release has Roslyn 5.12 (found from the bundled DLLs and the upstream PRs, not from a
   run). Wait for that release and update the pin in `.config/dotnet-tools.json`.
   Setting `LangVersion` to `preview` for Stryker only would mutate against the July
   Roslyn's preview, not the C# 15 that shipped; if P2 has to merge first, record Stryker
   as not run rather than passed.
5. **The Stryker runs confirm lesson 4 (2026-11-14).** `scripts/stryker-close.sh` on the
   P2 branch, with 5.0.0 and with 5.1.0, failed with CS0246 (`union` not found) in
   `Model/HandshakeOutcome.cs`: "Failed to restore the project to a buildable state", score
   0.00 %. P1 plus only the `[with(...)]` line in `Parser/HandshakeParserDelegate.cs` failed
   with CS8652 ("collection expression arguments is currently in Preview") on both versions.
   Neither file is the one Stryker mutates; Stryker compiles the whole project, so one
   construct anywhere stops every mutant. Logs: `docs/evidence/csharp-15/` on the P2 branch.
6. **Stryker exits 0 when it aborts.** After "Compilation failed" (FTL) and a 0.00 % score,
   `dotnet-stryker` returned 0: `scripts/stryker-close.sh` runs it under
   `set -euo pipefail` and still exited 0. The Pdd gate fails, on the missing report, but a
   direct run of the script looks green. Read the log or the report, not the exit code.
7. **The test server's small echoes wait 40 ms.** `LoopbackWebSocketServer.WriteFrameAsync`
   writes a frame's header and payload as two writes. With Nagle's algorithm, the second
   waits for the ACK of the first, which the client delays: a 32-byte echo took 44,869 µs, a
   64 KiB echo 142 µs. With one write per frame the 32-byte echo takes 16 µs, so the client is
   not affected. The P3 benchmark echoes with one write (`verification/runtime-async.md`).
   Every small echo in the tests pays the delay; nothing in them depends on latency.
