# 10.4 plan: .NET 11 and C# 15

Written 2026-11-14. Release 10.4.0 adds the `net11.0` target and uses what C# 15 and
.NET 11 offer inside the library. It adds no feature and no public API. The work is three
topic branches into `releases/10.4.0.0`, created from `main` at `9a6fbcc`, one pull request
each, merged in this order. Releasing stays the owner's step.

| Step | Work | Branch | Needs |
| --- | --- | --- | --- |
| P1 | `net11.0` target, LangVersion 15, .NET 11 test host, tooling, CI, dev container, docs | `chore/net11-platform` | none |
| P2 | C# 15 inside the library: a union for the handshake outcome, collection expression arguments | `chore/csharp-15` | P1 |
| P3 | Runtime Async for the `net11.0` build, adopted only if tests and measurements support it | `chore/runtime-async` | P1 |
| R | Release notes and README row, then the owner sets `GitVersion.yml` and versions | `docs/release-10.4.0` | P1 to P3 |

## Owner decisions (2026-11-14)

1. Keep `net8.0` and `net9.0` although both reached end of support on 2026-11-10, the day
   .NET 11 shipped. Dropping them would move .NET 8 and 9 consumers to the
   `netstandard2.1` build, whose `#if` paths differ: a behaviour change in a release
   that promises none.
2. Turn on Runtime Async (`<Features>runtime-async=on</Features>`) for `net11.0` only, as
   its own pull request, with the full evidence run and before and after numbers. If the
   tests or the numbers argue against it, report that instead of adopting it.
3. Adopt C# 15 where it fits: LangVersion 15 for every target, a union for the internal
   handshake outcome, with internal polyfills of the three compiler types for the targets
   before .NET 11, and `with(...)` collection expression arguments. Labeled `break` and
   `continue` have nothing to replace here (no nested loops), so they are not used.

## Facts checked on 2026-11-14

- .NET 11.0.0 and SDK 11.0.100 were released on 2026-11-10 (release metadata
  `releases-index.json`). C# 15 is the default for `net11.0`.
- With the 11.0.100 SDK and `LangVersion` 15, collection expression arguments and labeled
  `break`/`continue` compile for `netstandard2.0`, `net10.0` and `net11.0`. Union types need
  `System.Runtime.CompilerServices.IUnion` and `UnionAttribute`, and `closed` needs
  `IsClosedTypeAttribute`; only .NET 11 has them (errors CS0518 and CS0656 on the others).
- Runtime Async is off by default for `net11.0`: the SDK sets neither `Features` nor
  `UseRuntimeAsync`.
- Dafny 4.11.0 is self-contained on its own .NET 8 runtime, so the protocol job does not
  depend on the SDK version installed beside it.

## Lessons

1. **`Microsoft.Bcl.AsyncInterfaces` 11.0.0 does not support `net8.0` or `net9.0`.** Its
   build targets warn for both. The interface package references it unconditionally from
   its single `netstandard2.0` target, so the warning would reach every .NET 8 and 9
   consumer's build. Both projects stay on 10.0.14, with a comment in
   `IWebsocketClientLite.csproj`. Bump it with the decision to drop `net8.0` and `net9.0`,
   not before.
2. **The .NET 11 dev container images are Ubuntu 26.04 only.** `mcr.microsoft.com/devcontainers/dotnet`
   has `2-11.0` and `2-11.0-resolute` and no `noble` tag. CI host qualification requires
   Ubuntu 24.04, so the dev container keeps the `2-10.0-noble` image and its `dotnet`
   feature adds the 11.0 SDK. A move to 26.04 is its own change.
3. **The controlled experiments follow the newest target.** They, the Stryker runtime probe
   and Stryker itself used to name `net10.0`. They now use `Evidence.PrimaryTfm`
   (`net11.0`). That matters for P3: Runtime Async changes the `net11.0` build only, so the
   race experiments must run against that build to say anything about it.
